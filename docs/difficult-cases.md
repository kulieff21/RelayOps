# Difficult-case verification

Phase 14 validates persistent effects and failure boundaries against isolated fictional
records. Run `npm run check` for the full suite/build/public-release scan, followed by
`npm run smoke` for compiled HTTP startup. `npm run test:difficult` runs the 22 additional
combined/regression scenarios; existing focused suites are also required for the complete
matrix below. No real model, Telegram, supplier or payment request is needed.

The named demonstration, customer conversations, credentials and original shared model
ledger are preserved. The synthetic ledger costs used below are fixtures, not real spending.
These checks verify the specified sandbox boundaries, not production penetration testing
or live model performance.

## Observed defects and corrections

1. Case audit sorting used `created_at,id`. UUIDs have no chronological meaning and the
   frozen business clock gives multiple effects the same timestamp. The business-panel
   timeline could show receipt before purchasing or allocation before inspection. Sorting
   now uses `created_at,rowid`, the stable SQLite insertion order for tied timestamps.
   Public responses retain the same field shape; no internal sequence is exposed. The
   regression uses deliberately descending audit IDs and verifies committed causal order.

2. Adapter diagnostics copied a provider-supplied model ID after only a syntax check.
   A provider could reflect the authorization credential inside a valid-looking model ID;
   the diagnostic CLI prints this error object. Diagnostics now record only the fixed
   `configured`/`unexpected` classification. The response is still rejected, independent
   billing is still retained and no ambiguous inference retry is added. The regression
   verifies a reflected synthetic marker never enters the serializable diagnostic.

`secrets:check` is now part of the ordinary check/CI sequence after production compilation.
It is read-only, makes no provider/network request, and prints counts/fixed failures rather
than matching content or configuration values. It checks actual saved server keys/Telegram
IDs when `.env` is present; CI without that local file still checks credential signatures,
private-path exclusions, repository history and generated frontend assets.
